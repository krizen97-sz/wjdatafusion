## v4.8.3 文档额度语义与基线

- `doc_user_quota` 及其 `user_id / quota_bytes / max_upload_bytes / create_by / create_time / update_by / update_time` 七列早于 v4.4.1 就应存在。本次不新增表/列，不 ALTER 列注释，不补用户额度。
- `user_id`、`quota_bytes`、`max_upload_bytes` 必须是非空非生成 BIGINT；表使用 InnoDB。BIGINT（包括 UNSIGNED）原生可保存 0。
- `max_upload_bytes=104857600` 是 100 MiB（界面称 100 MB）；0 是不设个人单文件限制，但仍受剩余总空间及 Office/PDF 安全边界约束。新用户仍默认 100 MB，必须由管理员逐人选择无限制。本 SQL 不自动给任何人解除限制。
- 既有正数限制（含历史 1–99 MB）原值保留；`quota_bytes` 必须大于 0，`max_upload_bytes` 不得为负。额度记录中的用户、创建/修改时间也不改变。
- 若额度表存在自定义 CHECK 或 INSERT/UPDATE 触发器，预检保守阻断，由 DBA 检查它们是否限制或改写 0。即使约束看起来合法也不自动删除/绕过；DBA 应使用能查看目标表触发器元数据的升级账户。核验只查询元数据和聚合值，不通过试写真实用户来证明 0 可存。
- 缺表/列说明“完整 v4.4.1”前提未满足，不能把它当作 v4.8.3 新增 DDL。先结合目标库及历史发布记录审计遗漏的文档升级，单独制定补齐方案；不要盲目重跑早期脚本，其中可能含权限修改及默认额度初始化。
- 旧数据库注释“最大100MB”不会限制数值，也不会被本包修改；实际语义以上述应用契约为准。旧程序回退后可能把 0 当作默认100 MB，回退时需要再次向用户说明。

## 影响范围与冲突处理

- 正常新升级新增6行 `sys_menu` 和6行 `sys_role_menu`（role_id=1），ID由数据库分配，不占用固定ID。
- 只向正常且未删除的 `role_id=1 / role_key=admin` 授权。其他角色需要由管理员在平台内按职责授权，脚本不自动扩大权限。
- 与原历史脚本相比，累计脚本只授权明确的6项，不包含工作台下用户自建的其他子菜单。
- 不更新、删除既有菜单或角色记录；不会自动开启已有隐藏/停用菜单。已有正常部分配置可以补齐。
- 检查必需列、InnoDB、菜单自增ID、角色身份、菜单路径/组件/权限身份、重复按钮、跨目录权限和同名路由。发现冲突输出 `BLOCKED` 并报错，尚未写入永久表；文档基线/额度核验失败同样阻断。由管理员核对来源后处理，脚本不会挑一条覆盖。
- 预检使用会话临时表，需要 `CREATE TEMPORARY TABLES`、必要的 `SELECT` 和两张目标表的 `INSERT` 权限，不需要 `CREATE ROUTINE`。使用包含库名摘要的命名锁，防止本累计脚本并发执行；升级期间不要由其他会话编辑菜单，也不要并行执行旧脚本。
- MySQL5.7+/8.x兼容语法；本轮仅实测本地MySQL8.4.6。生产若使用其他版本，应先在该版本的库副本演练。

## 建议执行顺序

先完成应用与私有文件备份，再备份菜单及授权表。执行窗口内暂停菜单/角色管理变更。登录信息通过 MySQL login-path 或权限受限的客户端配置文件提供，不把密码写入命令或SQL。

以下命令在SQL目录执行，`rynew-upgrade` 为运维已配置的连接名，`TARGET_DB` 必须改为实际平台数据库。所有命令使用新批处理连接：

```bash
TARGET_DB='实际平台数据库名'
mysqldump --login-path=rynew-upgrade --single-transaction --no-tablespaces --set-gtid-purged=OFF "$TARGET_DB" sys_menu sys_role_menu sys_role doc_user_quota > before_v4_8_3_menus.sql
mysql --login-path=rynew-upgrade --database="$TARGET_DB" --default-character-set=utf8mb4 --batch < data_governance_upgrade_20260918_v4_4_1_to_v4_8_3_all.sql > upgrade_v4_8_3.log 2>&1
mysql --login-path=rynew-upgrade --database="$TARGET_DB" --default-character-set=utf8mb4 --batch < data_governance_verify_20260918_v4_8_3.sql > verify_v4_8_3.log 2>&1
```

每一步确认退出码为0再执行下一步，不要把这三行不加检查地整体粘贴执行。升级日志须出现全部 17 项检查 `PASS`、`UPGRADE_OK` 和锁释放成功；核验预期为 root=1、workspace=1、four_button_permissions=4、active_admin_role_1=1、admin_expected_grants=6。文档 5 项检查也应全部 PASS，核对输出的配置用户数、100 MB 用户数、无限制用户数和保留的其他正数额度人数。已有隐藏/停用状态会单独列出，应核对其是否符合预期。

**禁止 `--force`、忽略错误继续、仅执行选中部分或在已有未提交业务事务的连接内执行。** 预检异常会触发临时表重复主键错误（用于中断批处理），结合之前的 `BLOCKED` 项定位。任何SQL报错都先停止并断开该连接，让事务回滚；不得仅凭最后一条SELECT判断成功。预检额外防护不代表忽略中途DML错误后仍有完整事务保证。

数据库核验后，发布匹配的前后端与执行组件。重新登录平台，检查数据治理菜单、权限、任务列表及一条隔离预览流程。SQL核验不代表引擎或业务连接已就绪。文档上传还必须发布匹配后端/前端及精确路径 Nginx 配置，否则大文件仍可能 413；详见 [文档上传部署方案](../../deploy/document-management/UPLOAD_LIMITS_v4.8.3.md)。

## 非数据库文件必须独立保留

Kettle定义、输入文件、运行记录、计划、连接、冻结版本，以及NiFi已有流程数据使用配置指定的私有目录/引擎存储，不在这份SQL内。升级应用前备份这些实际配置目录并保持原权限、原加密密钥、Broker令牌与端点许可。v4.8.1含Worker上下文/超时契约更新，应同步部署配套Python、Java执行类及Linux适配器，不能仅换一个脚本或仅执行SQL。

不要执行 `ry_20260320.sql`、`support_deploy_all.sql` 或早期累计SQL来代替本增量包；它们不属于本版本区间，初始化文件含删表语句。也不要因版本号较低而自动重跑历史归属数据迁移。

## 回退

优先回退匹配的应用版本，保留这6项增量菜单和已有数据；v4.4.1应用下治理入口可能不可用，由管理员在平台中隐藏。SQL没有更改旧业务结构，不需要回退业务表。

如必须撤销菜单增量，先将升级前备份恢复到隔离库进行差异比对，仅删除本次实际新增的关联行和菜单ID（关联先删，按钮/页面/目录依次处理），并确认没有新增引用。不能按路径批量删除，也不能整表覆盖线上升级后的其他管理变更。对执行前已经存在的治理菜单和角色授权不得撤销。本包因此不提供会误删既有配置的“一键回滚SQL”。
