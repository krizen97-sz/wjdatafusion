# RYNEW v3.14.3 至 v3.15.2 数据库升级说明

## 版本变更结论

| 版本 | 数据库变化 |
| --- | --- |
| v3.15.0 | 新增知识中心六张 `kb_*` 表、默认知识空间与目录、2510–2513 菜单和 admin 角色权限 |
| v3.15.1 | 无数据库修改，继续使用 v3.15.0 表结构和权限 |
| v3.15.2 | 无数据库修改，离线图标库仅涉及前端资源 |

因此，从已经完成 v3.14.3 升级的数据库进入 v3.15.2，只需要执行知识中心 v3.15.0 的数据库变化。

## 文件选择

累计升级脚本：

```text
WDF100.0/sql/knowledge_center_upgrade_20260829_v3_14_3_to_v3_15_2_all.sql
```

独立版本脚本：

```text
WDF100.0/sql/knowledge_center_v3_15_0_20260826.sql
```

两种方式二选一。不要在同一升级流程中先执行独立脚本、再执行累计脚本。两份脚本均可重复执行，但重复选择交付路径会增加无意义的数据库操作和审计噪声。

安全回滚脚本：

```text
WDF100.0/sql/knowledge_center_v3_15_0_20260826_rollback.sql
```

回滚只移除知识中心菜单和角色菜单关系，不删除 `kb_*` 表或知识版本数据。确认业务数据永久不再需要时，才可以另行制定人工清理方案。

## 执行前检查

1. 确认当前数据库已经完成 v3.14.3 及以前的升级。
2. 备份当前数据库，并记录备份文件、当前应用提交和运行版本。
3. 确认现有文档管理表 `doc_document` 存在。
4. 确认 admin 角色 `role_id=1` 存在且未删除。
5. 确认菜单 ID 2510–2513 未被其他模块占用。
6. 如果已经存在 `kb_*` 表，先确认它们来自知识中心，不要覆盖同名自定义表。

累计脚本会再次执行上述关键检查；发现文档基线缺失、菜单冲突或已有知识表关键字段不匹配时会主动终止。

## 推荐上线顺序

```text
数据库备份
  -> 执行累计升级脚本
  -> 发布同一提交构建的 v3.15.2 后端
  -> 发布同一提交构建的 v3.15.2 前端
  -> 授予业务角色知识权限
  -> 验收知识与文档联动
```

MySQL 命令行示例：

```bash
mysql --default-character-set=utf8mb4 -h <host> -P <port> -u <user> -p <database> \
  < WDF100.0/sql/knowledge_center_upgrade_20260829_v3_14_3_to_v3_15_2_all.sql
```

不要把数据库密码写入脚本、命令历史或交付文档。

## 执行后验收

- `kb_space`、`kb_page`、`kb_tag`、`kb_page_tag`、`kb_page_document`、`kb_page_version` 共六张表存在。
- 默认空间“运维操作手册”只有一条，五个默认根目录各一条。
- 菜单 2510–2513 的组件和权限字符与脚本一致。
- admin 角色拥有 2510–2513 四条角色菜单关系。
- 原有 `doc_*` 表结构、文档、ACL 和文件数据未被修改。
- 使用有 `knowledge:page:write` 权限的账号连续保存两次，版本号连续递增且修改记录可回看。
- 本人文档、共享文档、无权文档、归档文档和回收站文档的附件联动继续服从现有文档权限。

## 回滚顺序

```text
停止新知识写入
  -> 执行安全回滚脚本
  -> 切回 v3.14.3 前后端
  -> 验证旧业务菜单和核心接口
```

安全回滚后 `kb_*` 数据仍然保留，后续重新升级时可恢复使用。数据库备份仍是最终回退保障，不能用菜单回滚替代备份。
