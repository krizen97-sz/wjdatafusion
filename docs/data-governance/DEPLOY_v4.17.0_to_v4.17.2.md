# v4.17.0 到 v4.17.2 数据库增量

整理日期：2026-10-26。起点是**完整部署的 v4.17.0**，目标是本次完成分支核对后的主线，包含 v4.17.1、v4.17.2 和已集成的原生 HDI 数据治理能力。

## 执行哪一份

已完整部署 v4.17.0：执行包内 `03_upgrade_v4_17_0_to_v4_17_2_all.sql`。这是唯一需要执行的累计增量；先后运行包内两份只读检查，核对结果后再升级。

还没有完成 v4.17.0：先按 `optional_before_v4_17_0/` 中的说明完成候选密码池迁移，再执行累计增量。原 v4.17.0 迁移要求完整 v4.16.0 基线；不要把本包用于补齐更早版本的全部缺项。

本次没有发布额外业务版本。v4.17.1 的扫描审计修复、v4.17.2 的巡检周月报精简都**不新增业务表结构**；以下 DDL 来自同期已集成的数据治理原生任务能力。历史试验分支中未发布的“v4.18.0 基础本地流程”没有重新启用，也不作为本包升级目标。

## 全部结构变化

| 表 | 用途 | 对已有数据的影响 |

| dg_hdi_schedule | 冻结修订的计划及领取状态 | 仅不存在时建表 |

## 部署顺序

1. 确认目标库及完整 v4.17.0 基线，备份业务库和当前程序，保留有效的 AES 密钥及私有任务存储。暂停应用写入和计划，使用独立数据库连接。
2. 运行 `01_check_v4_17_0_base.sql`。不得出现 STOP 或 SQL 错误。检查只报告，不会自动升级或修复问题。
3. 运行 `02_check_v4_17_0_to_v4_17_2.sql`。首次升级允许十张表为 NOT_APPLIED；已存在的表需按 sources 中的建表定义核对类型、默认值、主键和索引。出现 STOP 先处理，不能绕过后继续。
4. 执行 `03_upgrade_v4_17_0_to_v4_17_2_all.sql`，确认退出码为 0；不要使用 mysql 的 `--force` 选项。
5. 再运行两份只读检查。十张表均应存在，累计 SQL 的结构计数为 10；字段、主键、索引需与源定义一致，原业务及已有 HDI 行应保持不变。
6. 配套部署同一主线版本的前后端。巡检月报现在是一份 docx，不能混用仍按 zip 命名的旧前端。

命令示例使用交互密码，不把密码放进命令行或交付包：

```bash
mysql --host='实际地址' --port=3306 --user='部署账号' -p \
  --default-character-set=utf8mb4 --database='实际业务库' \
  < 01_check_v4_17_0_base.sql

mysql --host='实际地址' --port=3306 --user='部署账号' -p \
  --default-character-set=utf8mb4 --database='实际业务库' \
  < 02_check_v4_17_0_to_v4_17_2.sql

mysql --host='实际地址' --port=3306 --user='部署账号' -p \
  --default-character-set=utf8mb4 --database='实际业务库' \
  < 03_upgrade_v4_17_0_to_v4_17_2_all.sql
```

累计 SQL 会阻止缺少关键 v4.17.0 字段、已有目标表缺少必要列或存在自定义目标触发器的情况；它不会自动纠正已有表的错误类型、默认值或索引。IF NOT EXISTS 不代表已有定义已验收，前后只读核对仍须完成。

MySQL DDL 会隐式提交，整份升级不是一个可整体回滚的事务。中断后先查清已有对象，再修复原因并重跑，不要删除已写入数据的表重建。

## 运行与回退

本包只整理平台业务库增量，不安装或初始化 HDI 原产品数据库、Core、Agent、插件或授权文件。原生任务能力仍需按现有部署文档配置匹配的运行包；建表成功不表示外部运行环境已经就绪。

应用回退优先恢复配套旧程序和配置，保留新增表及其已产生数据。不要为了应用回退而 DROP 这些表、清空凭据池或覆盖整个业务库。继续保留升级前备份，必要的数据定向恢复另行核对。
