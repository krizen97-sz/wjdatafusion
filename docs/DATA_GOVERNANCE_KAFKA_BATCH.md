# 数据治理 v4.7.0：Kafka有界批次

本版提供实际Kafka取批、不可变处理配置执行、可选FTP交付和显式消费位点确认。`Kafka批次`页操作专属消费组；普通Cron计划目前仍重复固定JSON输入，不会自动轮询Kafka。

## 接入范围

默认关闭`data-governance-kafka.enabled`，不会启动网络客户端或初始化源存储。独立测试环境显式启用，允许的broker默认`127.0.0.1:19092`。使用同步、有帧/总字节/解析预算和绝对时限的Kafka协议通信，每一次bootstrap、leader和coordinator连接都核对允许地址；没有后台自动提交或隐藏metadata连接。

当前要求现代flexible协议、IPv4/PLAINTEXT、magic v2、未压缩/非事务/非墓碑UTF-8记录，读取模式READ_UNCOMMITTED。压缩、事务、控制batch和不支持协议会明确失败，不确认位点。它不是旧ZooKeeper消费组或任意Kafka认证部署的直接替换。

## 批次及租约

一次最多100条，包装后最多256KiB。每行保留原`k_message`及topic/partition/字符串offset；前端不经浮点数改写位点。消息过大、坏UTF-8、分区不完整、响应CRC/长度/关联号异常等使整批失败。

专属组须使用`rynew-governance-<owner>-`前缀。相同源/消费组有持久本地租约；未处理批次不能并行重取。next-offset只来自真正纳入本批次的记录，不提交prefetch位置，不要求日志位点无空洞。

取批保存原committed、起始、目标位点和原始输入SHA。未执行/未提交意图的批次可显式放弃本地占用，Kafka位点不变。已保留执行、关联运行或尝试确认的批次不能通过普通释放绕过核查。

## 执行与确认

选择已发布版本时，只复用其处理图、参数、组件版本和字典；本次Kafka输入生成新的执行快照。保存原releaseHash、新executionHash及inputSHA，原版本不会改变。先持久计划runId并保留源执行意图，再提交真实NiFi，随后验证owner/inputSHA关联。重复execute不会创建第二个运行。

运行成功且清理/完整产物确认后，才进入可选FTP交付；目标指纹须与原意图一致。EMPTY必须没有矛盾的输出/manifest，才明确跳过FTP。失败不交付、不确认。HTTP状态查询不会暗中启动处理或FTP。

处理完成后，用户显式确认位点。服务端重新检查真实运行、完整文件内容/摘要及必要的FTP完成状态；提交前后读取实际broker位点。不倒退，不越过未处理尾部；回复不明确保持COMMIT_UNKNOWN和租约，重试首先读实际位点。初始/目标混合状态仅对仍在原值的分区继续确认，其他冲突不写。

重启未完成执行保留待核查，恢复只查已有run和交付；缺失run或未知发送效果不会自动重放。当前已关联失败的执行需核查处理，不提供无条件抹除执行意图的按钮。

## 验证与边界

- 独立Kafka4.1.2：双分区125条记录只取100，位点确认前为空；确认后只推进实际处理分区，25条尾部下次仍可读。
- 真实6条Kafka消息→新的执行快照→NiFi完整文件→FTP，确认前broker位点仍为空；显式确认后两分区均为3，下次取批为空。
- 所有失败、超限和未完成交付均不确认。合成主题与测试组在独立本机broker运行。

原任务白名单Kafka回写、持续消费/自动Kafka取批调度、旧组位点迁移、逐批实时数据库查询及生产认证配置仍未接入。两条业务图中的Kafka回写分支目前为保留原消息的待发送产物，不能以输入链路测试通过代替生产输出验收。
